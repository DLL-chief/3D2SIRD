# ADR-004: Стереограмма в реальном времени — пул воркеров по строкам, а не GPU

**Статус:** Принято
**Дата:** 2026-09-15
**Авторы:** Дима (решение), Claude Code (замеры и реализация)

## Контекст

`ADR-003` отложил режим реального времени и заранее оговорил: «если
понадобится — новый ADR со ссылкой на этот». Понадобилось: владелец
попросил, чтобы стереограмма менялась во время вращения модели, а не после
отпускания кнопки.

Замеры на 968×678 (Chromium, 4 ядра, WebGL через SwiftShader):

| участок | время |
|---|---|
| `depth/` — рендер, чтение пикселей, нормализация, размытие | 52 мс |
| `sird/` — генератор в одном воркере | 66 мс |
| вся цепочка | 125 мс → 8 кадр/с |

То есть узкое место не в одном месте, а в двух сразу, и генератор — большая
половина. Внутри генератора львиную долю съедает проверка окклюзии: она
делает в среднем **17.5 итераций на пиксель** (замер на полусфере).

## Решение

Три шага, без замены алгоритма:

1. **Кадр считается полосами в пуле воркеров** (`src/sird/pool.js`).
   В алгоритме TIW строки независимы друг от друга: массив ссылок `same`
   живёт внутри строки, и наружу из неё ничего не выходит. Поэтому кадр
   делится на горизонтальные полосы по числу ядер, и результат обязан
   совпадать с расчётом целиком. Единственное, что зависело от номера
   строки, — выбор цвета из узора, поэтому `generate()` принимает
   `rowOffset`.
2. **Черновик при вращении.** Пока мышь ведёт модель, цепочка считается в
   уменьшенном масштабе и растягивается на полотно без сглаживания; по
   завершении жеста идёт итоговый кадр пиксель в пиксель. Уменьшение бьёт
   по обоим участкам сразу, включая рендер глубины.
3. **Масштаб черновика подстраивается по факту** (`src/ui/draft-scale.js`),
   а не задаётся константой: скорость зависит от числа ядер, GPU и размера
   кадра, и число, подобранное на одной машине, на другой врёт.

## Результат замеров

| конфигурация | генератор | вся цепочка |
|---|---|---|
| 968×678, 1 воркер | 66 мс | 125 мс (8 кадр/с) |
| 968×678, 4 воркера | 35 мс | 95 мс (10.5 кадр/с) |
| 581×407 (черновик 0.6), 4 воркера | 20 мс | 46 мс (22 кадр/с) |

Параллельный кадр сверен с одиночным побайтово: **0 расхождений из 480 000
байт**. Замеры сделаны на программном WebGL (SwiftShader) и 4 ядрах — на
машине с настоящей видеокартой и большим числом ядер цифры будут лучше.

## Альтернативы

- **GPU-версия (фрагментный шейдер / WebGPU).** Отклонена по причинам из
  ADR-003, которые не изменились: алгоритм последовательный внутри строки,
  а приближённые GPU-варианты дают артефакты на резких перепадах глубины.
  Отдельный довод против: владелец уже забраковал картинку из-за грубого
  рельефа (10 ступеней вместо 27) — менять качество на скорость здесь
  ровно то, чего он не хочет. Пул воркеров даёт скорость, не трогая
  результат.
- **Оптимизировать проверку окклюзии** (ограничить число итераций сверху).
  Отклонена: это и есть та самая точность на границах объекта, из-за
  которой алгоритм выбран. Ускорение получилось бы за счёт «двоения»,
  которое ADR-003 называет главным фактором читаемости.
- **Считать только изменившиеся строки.** Отклонена: при вращении модели
  меняется весь кадр, экономии не будет.
- **Постоянный масштаб черновика.** Отклонена: см. п.3 решения.

## Последствия

- `src/sird/generate.js` получил третий аргумент `rowOffset`. Полный кадр
  по-прежнему считается одним вызовом — контракт из
  `docs/api_contracts.md` не меняется.
- Появился инвариант, который надо держать: **деление на полосы не меняет
  результат**. Он закреплён тестом `src/sird/__tests__/bands.test.js` —
  если кто-то введёт в генератор состояние, живущее между строками, тест
  упадёт.
- Пул держит N воркеров на всё время жизни страницы. При `hardwareConcurrency`
  больше 8 берётся 8: дальше выигрыш съедается склейкой кадра.
- Ограничение осталось: цепочка вызывается из главного потока, и рендер
  глубины по-прежнему синхронно читает пиксели из GPU. Если понадобится
  ещё быстрее, следующий шаг — не GPU-генератор, а асинхронное чтение
  (`readRenderTargetPixelsAsync`) и/или карта глубины меньшего разрешения
  с повышением на CPU.
