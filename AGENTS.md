# AGENTS.md — единые правила для ИИ-агентов

Этот файл — стандарт кодирования и поведения для ЛЮБОГО ИИ-ассистента,
работающего в этом репозитории: Claude, Grok, Copilot, локальные модели и
другие. Параметры, специфичные для конкретного инструмента (например, для
Claude Code) — в отдельном файле, который на этот ссылается (см. `CLAUDE.md`).

## 1. Обязательное правило — всегда

**По завершении ЛЮБОЙ задачи — открыть `STATUS.md` и обновить его**:
перенести пункт из «В работе» в «Сделано», зафиксировать новые блокеры,
поправить ближайший беклог. Работа без обновления `STATUS.md` считается
незавершённой, даже если код рабочий и запушен: следующий агент/разработчик
не узнает об этом иначе.

## 2. Стек и границы

- Стек зафиксирован в `README.md`, п.2: Vite + vanilla JS + Three.js, без
  фреймворка, без бэкенда. Агент не расширяет стек по своей инициативе —
  новая зависимость (кроме dev-инструментов вроде линтера) требует ADR.
- Модуль `src/sird/` не должен импортировать Three.js — он работает с голым
  массивом глубин (см. `docs/architecture.md`, инварианты). Это правило
  проверяется на ревью.
- Не отключать и не удалять проверки/линтеры/тесты ради зелёного CI —
  чинить причину, а не индикатор.

## 3. Стиль кода

- Следовать существующему стилю файла/модуля, а не личным предпочтениям
  модели.
- Без комментариев, объясняющих ЧТО делает код (это видно по именам) —
  только когда есть неочевидное ПОЧЕМУ (обходной путь, скрытое ограничение,
  история конкретного бага). Исключение — формулы алгоритма стереограммы:
  ссылка на источник и смысл переменных обязательны.
- Не добавлять абстракции, обработку ошибок и фичи «на будущее» — только то,
  что нужно для текущей задачи. Три похожие строки лучше преждевременной
  абстракции.
- Перед правкой существующего модуля — прочитать его локальный `README.md`,
  если он есть (см. `src/README.md`).

## 4. Коммиты и PR

- Формат коммита: `<область>: <что сделано, повелительное наклонение>`,
  например `sird: добавить учёт окклюзии в проходе по строке`. Тело коммита —
  это «почему», а не «что».
- Один PR — одна логическая задача. Не смешивать рефактор и фичу.
- Описание PR — по-русски: что сделано и зачем, ссылка на issue.
- Прямой пуш в `main` — только если это явно разрешено в `CLAUDE.md`; по
  умолчанию — через PR.

## 5. Источник правды

- Технические решения фиксируются в `docs/`, а не остаются в переписке или
  памяти агента (см. `docs/adr/001-gitlab-single-source-of-truth.md` — для
  этого проекта репозиторий на GitHub, принцип тот же).
- Значимые архитектурные решения — новый ADR в `docs/adr/` со сквозным
  номером; принятые ADR не редактируются задним числом.
- Расхождение между кодом и `docs/` — чинить документацию сразу в том же
  PR, а не откладывать.

## 6. Чего не делать

- Не выдумывать метрики и факты — если данных нет, ставить `TODO` и
  спрашивать владельца.
- Не коммитить бинарные 3D-модели и текстуры размером больше ~1 МБ в
  репозиторий — для тестовых ассетов использовать маленькие файлы или
  генерировать геометрию кодом (`THREE.TorusKnotGeometry` и т.п.).
- Не удалять `STATUS.md`/`docs/adr/*` «для чистоты».
